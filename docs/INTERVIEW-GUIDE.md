## 타임딜 서비스 인터뷰/발표 정리

이 문서는 타임딜 서비스 프로젝트를 **면접·발표용으로 설명할 때** 사용할 수 있는 요약과  
예상 질문/답변을 정리한 가이드입니다.

---

## 1. 한 줄 소개

- **프로젝트 한 줄 요약**
  - 특정 시간에 주문이 몰리는 **타임딜 상황**에서,  
    **주문·재고 정합성을 지키면서 성능·레질리언스·관찰성까지 실험으로 검증한 Spring Boot 서비스**입니다.

---

## 2. 문제 정의 · 목표

- **문제**
  - 하나의 상품에 수백 명이 동시에 주문하면,
    - 재고가 음수가 되거나,
    - 실제 재고와 주문 수량이 어긋나거나,
    - 응답 시간이 수 초 이상 길어질 수 있습니다.

- **목표**
  1. **재고/주문 정합성**을 100% 보장하면서
  2. **SLO**(피크 시 p95, 에러율, RPS)를 정하고
  3. 다른 **락 전략과 튜닝(캐시, 커넥션 풀, 레질리언스)을 실험**으로 비교·검증하는 것.

---

## 3. 아키텍처·기술 스택 요약

- **Backend**: Spring Boot 4.0.2, Java 21, Spring Data JPA, Querydsl 5.1.0
- **DB/캐시**: MySQL 8.0, Redis 7, Caffeine 캐시
- **보안**: Spring Security, JWT (로그인/로그아웃, 토큰 블랙리스트)
- **레질리언스**: Resilience4j RateLimiter, CircuitBreaker
- **관찰성**: Actuator, Micrometer, Prometheus, Grafana
- **부하 테스트**: k6 + perf 프로파일
- **문서화**: PERF_TEST_PLAN, PERF_RESULT, 락 전략 비교, 배포·모니터링 가이드 등

레이어 구조는 `domain / service / controller / infrastructure` 로 나뉘어 있고,  
락·보안·로깅·저장은 모두 `infrastructure` 아래로 모으는 방향으로 정리했습니다.

## 4. 락 전략 설계 (비관적 / 낙관적 / 분산 락)

### 4.1 세 가지 전략

- **비관적 락 (Pessimistic)**
  - JPA `@Lock(PESSIMISTIC_WRITE)` → `SELECT ... FOR UPDATE`
  - 재고 행을 DB 레벨에서 잠궈서 **한 번에 한 트랜잭션만 수정**.
  - 장점: 정합성 보장이 단순, 충돌 빈도가 높을수록 유리.
  - 단점: 경합이 많으면 대기 시간이 길어져 **레이턴시·처리량 저하**.

- **낙관적 락 (Optimistic)**
  - 엔티티 `@Version` + `saveAndFlush` 시 version 비교.
  - version 충돌 시 `OptimisticLockException` → 최대 3회 재시도, 이후 4xx 매핑.
  - 장점: 충돌이 드문 환경에서 락 대기 없이 빠르게 처리.
  - 단점: 동일 상품 몰림 시 **충돌/재시도/실패율 폭증**.

- **분산 락 (Redis)**
  - `stock:lock:{itemId}` 키로 `SET NX PX ttl` 사용.
  - 락을 가진 인스턴스만 재고 조회·차감·저장 후 Lua 스크립트로 “본인일 때만 delete”.
  - TTL/재시도 정책은 `application-perf-distributed.yml` 으로 외부화:
    - `ttl-seconds`, `max-retries`, `retry-sleep-ms`

### 4.2 전략 선택 로직

- `order.lock-strategy` (pessimistic / optimistic / distributed) 를 설정으로 받아  
  같은 코드/같은 k6 스크립트로 **전략만 바꿔서 실험**할 수 있도록 했습니다.
- 이 값은 `application-perf.yml` + `application-perf-optimistic.yml` + `application-perf-distributed.yml`  
  조합으로 프로파일별로 쉽게 전환할 수 있게 했습니다.

## 5. 성능 테스트 전략 & 결과 요약

### 5.1 성능 테스트 계획 (PERF_TEST_PLAN)

- **SLO 초안**
  - 일반 트래픽: p95 ≤ 300ms, 5xx < 0.5%
  - 타임딜 피크: p95 ≤ 1s, 5xx < 1%, 재고/주문 정합성 100%
- **시나리오**
  - A: 기본 READ (목록/상세)
  - B: 타임딜 스파이크 – 재고 부족
  - C: 타임딜 스파이크 – 재고 충분 (상품 분산)
  - D: Soak (장시간 혼합 부하)
- **실험 축**
  - 커넥션 풀 크기, 캐시 도입, 락 전략, 레이트리미터/서킷브레이커 등.

### 5.2 결과 핵심 (PERF_RESULT)

- **기본 READ**: p95 < 50ms, 에러 0%, 약 40 RPS
- **타임딜 스파이크**:
  - 재고 부족: 모든 요청 400(비즈니스 에러), 정합성 유지
  - 재고 충분: 약 160 RPS, p95 ≈ 950~960ms, 에러 0%, 주문 수천 건 성공
- **락 전략 비교 (실험 4)**:
  - 비관적: RPS ≈ 162, p95 ≈ 935ms, 실패 0%
  - 낙관적: RPS ≈ 145, p95 ≈ 1170ms, 실패율 23%대
  - 분산 락: RPS ≈ 132, p95 ≈ 1770ms, 실패율 40%+  
    → **동일 상품 몰림** 상황에서는 비관적 락이 가장 안정적.
- **레질리언스 실험 (실험 5)**:
  - RateLimiter(초당 100건), CircuitBreaker 적용 후  
    429/503 로 과부하와 장애 전파를 제어함.
- **장애 시나리오**:
  - DB 다운 시 100% 실패 후, 복구 시 정상 수렴.
  - Redis 다운 시, 현재 k6 시나리오에서는 주문 흐름에는 영향 없음(로그아웃 경로에만 의존).

> 단순 수치 나열보다는, **“SLO를 정하고 → 실측 결과를 보고 → 목표를 현실에 맞게 조정”** 하는  
> 과정 자체를 문서에 녹여 둔 것이 포인트입니다.

## 6. 레질리언스 (Rate Limiting / Circuit Breaker)

- **Rate Limiter (Resilience4j)**
  - 주문 생성 API에 `@RateLimiter(name = "orderCreate")` 적용.
  - 초당 N건 이상 요청은 429로 차단해서,  
    DB·락 경합이 심해지기 전에 **앞단에서 부하를 조절**.

- **Circuit Breaker (Resilience4j)**
  - `OrderService.createOrder` 에 `@CircuitBreaker` 적용.
  - DB 연쇄 장애 시 일정 실패율 이상이면 회로를 열어  
    내부 자원을 보호하고, fallback으로 503을 반환.

- **예외 매핑 및 k6 연동**
  - GlobalExceptionHandler 에서 429/503 을 명시적으로 처리해  
    클라이언트/부하 테스트에서 구분 가능하게 했고,
  - k6 스크립트에도 429/503 카운터를 추가해  
    “적용 전/후에 실패 패턴이 어떻게 바뀌는지”를 함께 비교했습니다.

## 7. 관찰성 (Prometheus + Grafana)

- **Prometheus**
  - Spring Boot Actuator `/actuator/prometheus` 노출.
  - Docker Compose 로 Prometheus 컨테이너를 띄워  
    `host.docker.internal:8080` 에서 메트릭 스크래핑.

- **Grafana**
  - Provisioning으로 Prometheus 데이터소스 및 **Timedeal 대시보드** 자동 로드.
  - 주요 패널:
    - HTTP 요청률 (URI별 RPS)
    - 주문 생성 호출률/응답 시간 (결과별)
    - JVM 메모리 사용량
  - k6 실험 중 실시간으로 RPS·레이턴시·에러 패턴·메모리 추이를 관찰.

- **문서화**
  - `deployment-monitoring.md` 에
    - docker compose 기동,
    - Prometheus 타깃 확인,
    - Grafana 접속 및 대시보드 사용법,
    - “No data” 트러블슈팅까지 정리.

## 9. 예상 질문 & 답변

### Q1. 왜 결국 비관적 락을 선택했나요?

**A.** 실험 결과, **동일 상품에 주문이 몰리는 타임딜 피크** 상황에서는  
낙관적·분산 락 모두 **충돌/경합 때문에 실패율과 레이턴시가 크게 증가**했습니다.

- 낙관적 락은 version 충돌이 매우 빈번하게 발생해서  
  3회 재시도로도 충분히 흡수되지 않았고, 5xx/4xx 비율이 높아졌습니다.
- 분산 락은 Redis 네트워크 왕복 + 경합으로 p95가 가장 크게 나왔고,  
  재시도 정책을 바꿔도 한계가 있었습니다.
- 반면 비관적 락은 DB 레벨에서 한 번에 한 트랜잭션만 처리하면서  
  정합성을 단순하게 보장했고, 이 부하 패턴에서는 RPS/p95/실패율이 가장 안정적이었습니다.

그래서 **“타임딜 스파이크”라는 도메인에 한정하면 비관적 락이 가장 적합하다**는 결론을 냈습니다.  
해당 이유와 수치는 `PERF_RESULT` 실험 4에 정리했습니다.

---

### Q2. 그렇다면 낙관적 락과 분산 락은 쓸모가 없나요?

**A.** 그렇지 않습니다. **도메인에 따라 적합한 곳이 다릅니다.**

- **낙관적 락**
  - 동시 수정이 드문 도메인(예: 내 프로필 수정, 일반 CRUD)에서는  
    락 대기 없이 처리할 수 있어 성능상 유리합니다.
  - 이 프로젝트에서는 “동일 상품 스파이크”라는 극단적인 케이스를 실험한 거라  
    낙관적 락이 불리하게 나온 것이고, 도메인에 따라 충분히 좋은 선택이 될 수 있습니다.

- **분산 락**
  - 멀티 인스턴스·멀티 리전 환경에서 **DB 락만으로는 커버가 안 되는** 케이스에 유용합니다.
  - 예를 들어, “인스턴스 수가 매우 많고, 재고 DB가 샤딩되어 있는 환경”에서는  
    Redis나 ZooKeeper 같은 외부 분산 락 서비스가 필요할 수 있습니다.
  - 이 프로젝트에서는 단일 DB + 비교적 단순한 구조라,  
    “같은 부하 조건에서라면 비관적 락이 더 낫다”는 정도까지 검증했다고 보는 게 맞습니다.

---

### Q3. 락 타임아웃과 재시도 전략은 어떻게 정했나요?

**A.** 두 레벨에서 생각했습니다.

1. **DB 락 타임아웃 (비관적 락)**
   - MySQL `innodb_lock_wait_timeout` 기본값(50초)은 타임딜 스파이크에는 너무 깁니다.
   - 스파이크에서 누가 한 번 락을 오래 쥐면 뒤에 오는 요청들이  
     10~50초까지 줄 서서 기다리는 상황이 생길 수 있기 때문에,
   - **5~10초 정도로 줄여서 “길게 기다리기보다는 조기 실패”** 쪽을 택했습니다.

2. **재시도 전략 (낙관적·분산 락)**
   - 낙관적 락: 최대 3회 재시도, 필요 시 지수 백오프(10/20/40ms) 고려.
     - 재시도 횟수를 늘리면 성공률은 오르지만, 레이턴시와 DB 부하가 늘어납니다.
   - 분산 락: TTL 5초, 3회 재시도, 10ms 대기.
     - TTL은 “한 번의 재고 갱신이 5초 안에 끝나야 한다”는 가정이고,
     - 재시도 정책은 `order.distributed-lock.*` 설정으로 쉽게 튜닝 가능하게 만들었습니다.

요약하면, **“무조건 성공할 때까지 기다리는 것”보다  
“적당히 기다려보고, 안 되면 빠르게 실패시키는 것”이 스파이크 상황에서는 낫다**고 판단했습니다.

---

### Q4. 실제 운영이라면 어떻게 가져갈 건가요?

**A.** 이 프로젝트의 부하 패턴을 실제 서비스라고 가정하면:

1. **기본 전략**: 비관적 락 기반 재고 차감
2. **DB 세팅**: `innodb_lock_wait_timeout` 을 5~10초 수준으로 조정
3. **레이트리미터**: 주문 API에 초당 N건 제한을 두어 과도한 스파이크 차단
4. **서킷브레이커**: DB/외부 의존성이 불안정할 때 회로를 열어 내부 보호
5. **관찰성**: Prometheus+Grafana 대시보드 기반으로 RPS/p95/에러율 모니터링

그리고, 도메인에 따라 일부 API는 낙관적 락이나 분산 락으로 전환할 수 있습니다.  
이 때는 이번 프로젝트처럼 **먼저 SLO를 정하고 → 실측으로 비교**하는 접근을 반복할 것 같습니다.

---

### Q5. k6와 Grafana를 왜 같이 썼나요?

**A.** k6만으로는 **응답 시간/에러율/RPS** 같은 “결과 숫자”만 볼 수 있고,  
내부적으로 **JVM, DB 풀, 메모리, 특정 메서드 타이머**가 어떻게 움직이는지 보기가 어렵습니다.

- k6 → **바깥에서 본 지표** (사용자가 느끼는 응답, 성공/실패 비율)
- Grafana → **안에서 본 지표** (JVM 메모리, http_server_requests, timedeal.order.create 타이머 등)

두 개를 동시에 보면서:

- 같은 부하에서 **레이트리미터/서킷브레이커/락 전략 변경이  
  RPS·p95·에러율·메모리에 어떤 영향을 주는지**를 더 입체적으로 볼 수 있었습니다.

---

### Q6. 이 프로젝트에서 가장 어려웠던 점은 무엇이었나요?

**A.** 두 가지였습니다.

1. **“실험 설계”를 문서로 정리하는 것**
   - 단순히 코드를 바꾸고 k6를 돌리는 것을 넘어서,
     - 어떤 시나리오를 어떤 공통 조건에서 비교할지,
     - SLO를 어떻게 정의하고,
     - 결과를 어떤 구조로 문서에 담을지 정하는 것이 생각보다 시간이 많이 들었습니다.

2. **실험을 해석하고 결론까지 가져가는 것**
   - 예를 들어, 낙관적 락이 실패율이 높게 나왔을 때
     - 단순히 “느리다”가 아니라,
     - 어떤 상황에서 왜 그런지,
     - 그럼 언제 쓰는 게 맞는지까지 정리하는 게 중요하다고 느꼈습니다.

이 과정을 통해, **어떤 기술을 “좋다/나쁘다”로 단정짓기보다  
“어떤 상황에서 어떤 트레이드오프를 가진다”** 로 설명하는 연습을 할 수 있었습니다.

### Q7. 앞으로 더 개선하고 싶은 점이 있나요?

**A.** 몇 가지가 있습니다.

1. **분산 락 고도화**
   - 현재는 Redis 단일 인스턴스를 기준으로 했는데,  
     Redisson이나 RedLock 알고리즘을 적용한 다중 노드 환경까지 확장해보고 싶습니다.
2. **자동화된 실험 파이프라인**
   - k6 스크립트 실행 → Prometheus에서 결과 수집 → 요약 리포트 생성까지  
     일부 자동화해서, 파라미터만 바꾸고 여러 번 실험을 돌리기 쉽게 만들고 싶습니다.
3. **실제 클라우드 환경 반영**
   - 로컬 Docker 대신, 클라우드 환경(K8s 등)에 배포해서  
     네트워크 레이턴시, 오토스케일링까지 포함한 실험도 해보고 싶습니다.
