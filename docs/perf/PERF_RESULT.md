# 타임딜 서비스 성능 테스트 결과

> 이 문서는 **공통 조건을 한 번 정하고**, 그 조건에서 **변수 하나씩만 바꾼 실험**으로 결과를 정리한 리포트입니다.  
> **1절**에서 공통 조건, **2절**에서 부하 시나리오 정의, **3절**에서 Baseline 수치, **4절**에서 실험별 비교를 둡니다.  
> 계획·SLO는 [PERF_TEST_PLAN.md](PERF_TEST_PLAN.md)를 참고하세요.

## 0. 한 페이지 요약

- **대상**: 타임딜 서비스(Spring Boot, JWT·Redis·MySQL)의 주문/재고·READ·Soak 성능을 k6로 측정한 결과.
- **공통 조건**: **1절**에 정의. 프로파일 `perf`, Hikari 풀 30/10, 캐시 없음, 비관적 락, 인덱스 적용, 주문 시나리오는 재고·오픈 조건 명시.
- **부하 시나리오**: **2절**에 정의. A=basic-read(20 VU 60s), B=order-spike(0→200 VU 10s+60s, ITEM_ID=1 재고 충분), C=order-spike-distributed(동일 stages, 전체 상품 재고·오픈 충분), D=soak-mixed(10 VU 10분).
- **Baseline**: **3절** 한 표. 위 공통 조건 + 2절 시나리오로 측정한 A·B·C·D 각각의 RPS·p95·에러율·주문 성공 수.
- **실험**: **4절**에서 변수 하나씩만 바꾼 비교. 실험 1=재고 수준(부족 vs 충분), 2=Hikari 풀(30/10 vs 50/20), 3=캐시(없음 vs Caffeine), 4=락 전략(비관적 vs 낙관적). 각 실험마다 "바꾼 것 / 나머지 1절·2절과 동일"을 명시.
- **부하 유형 비교**: **5절**. order-spike vs order-spike-distributed는 요청 구성·지표 정의가 다르므로 "동일 조건 실험"이 아니라 "부하 유형이 다른 시나리오 비교"로 분리.
- **결론**: **6절**. **SLO 대비**는 6절 내 소절로 정리.
- **장애/에러 시나리오**: **7절** (선택). DB/Redis 일시 중단·복구 시 에러·동작 기록 구조. 실행 절차는 PERF_TEST_PLAN 5.4 참고.

## 2. 부하 시나리오 정의

수치는 **3절 Baseline**에만 둡니다. 여기서는 **무엇을 어떻게 부하 거는지**만 정의합니다.

| ID | 이름 | 스크립트 | 부하 | 대상 API |
|----|------|----------|------|----------|
| **A** | basic-read | `perf/k6/basic-read.js` | 20 VU, 60초 | `GET /api/items`, `GET /api/items/{id}` |
| **B** | order-spike | `perf/k6/order-spike.js` | 0→200 VU(10s), 200 VU 유지(60s) | `POST /api/auth/login`, `POST /api/orders` (ITEM_ID=1 고정) |
| **C** | order-spike-distributed | `perf/k6/order-spike-distributed.js` | 0→200 VU(10s), 200 VU 유지(60s) | 로그인, `GET /api/items`, `POST /api/orders` (목록에서 랜덤 아이템) |
| **D** | soak-mixed | `perf/k6/soak-mixed.js` | 10 VU, 10분 | 로그인, 목록, 상세, 주문(약 30% 확률) |

- **B**는 동일 아이템(ITEM_ID=1)에만 주문이 몰리는 패턴.
- **C**는 iteration마다 목록 조회 후 **여러 아이템 중 랜덤 선택**해 주문하는 패턴. 요청 수·구성이 B와 다름.

## 3. Baseline 결과

**조건**: 1절 공통 조건 + 2절 시나리오 그대로 1회씩 측정.

| 시나리오 | RPS (http_reqs) | p95 | http_req_failed | orders_success_201 | 비고 |
|----------|-----------------|-----|-----------------|--------------------|------|
| A (basic-read, 20 VU 60s) | ≈ 38.5 | ≈ 38.8ms | 0% | — | 목록·상세만 |
| B (order-spike, 재고 충분) | ≈ 161 | ≈ 963ms | 0% | ≈ 6505 | ITEM_ID=1, 인덱스 O |
| C (order-spike-distributed) | ≈ 247 | ≈ 863ms | 0% | ≈ 6685 | 전체 상품 재고·오픈 충분 |
| D (soak-mixed, 10 VU 10분) | ≈ 29.3 | ≈ 118ms | 0% | — | 로그인+목록+상세+30% 주문 |

- B·C의 RPS·p95는 **동일 stages**이어도, C는 iteration마다 목록 조회가 들어가 요청 수가 많아져 RPS가 더 크고, 락이 여러 행에 나뉘어 p95는 B보다 낮게 나올 수 있음. 비교 시에는 **5절 부하 유형 비교**를 참고.

## 4. 실험별 비교

각 실험에서 **바꾼 것**은 한 가지뿐이고, **나머지는 1절 공통 조건 + 2절 시나리오**와 동일합니다.

---

### 실험 1. 재고 수준 (order-spike만)

- **목적**: 주문 스파이크 시 "재고 부족" vs "재고 충분"에서 처리량·에러율·정합성 차이 확인.
- **바꾼 것**: B 데이터 조건만 "재고 부족" vs "재고 충분"(ITEM_ID=1, open_time 과거, quantity 부족/충분).
- **나머지**: 1절·2절 동일 (풀 30/10, 캐시 없음, 비관적 락, 인덱스 O, 동일 k6 스크립트·stages).

| 지표 | 재고 부족 | 재고 충분 |
|------|-----------|-----------|
| RPS | ≈ 165 | ≈ 161 |
| p95 | ≈ 950ms | ≈ 963ms |
| http_req_failed | ≈ 50% (비 2xx 다수) | 0% |
| orders_success_201 | 0 | ≈ 6505 |
| orders_400_insufficient_stock | ≈ 6690 | 0 |

**해석**: 재고 부족 시에는 전부 `INSUFFICIENT_STOCK`(400)으로 응답하며 데이터 정합성 유지. 재고 충분 시에는 전부 201 성공. 두 경우 모두 p95 ≈ 1초 내외로 응답.

---

### 실험 2. Hikari 풀 크기 (30/10 vs 50/20)

- **목적**: connection pool 크기 변경이 A·B·D에서 RPS·p95에 미치는지 비교.
- **바꾼 것**: Hikari `maximum-pool-size`·`minimum-idle` 만 30/10 → 50/20 (환경변수로 오버라이드).
- **나머지**: 1절(풀만 제외)·2절 동일. 캐시 없음, 비관적 락, 인덱스 O.

| 시나리오 | 지표 | Baseline (30/10) | 조정 (50/20) |
|----------|------|------------------|--------------|
| A (20 VU 60s) | RPS | ≈ 38.5 | ≈ 38.5 |
| A (20 VU 60s) | p95 | ≈ 38.8ms | ≈ 34ms |
| B (재고 충분) | RPS | ≈ 161 | ≈ 167.6 |
| B (재고 충분) | p95 | ≈ 963ms | ≈ 987ms |
| D (10 VU 10분) | RPS | ≈ 29 | ≈ 29 |
| D (10 VU 10분) | p95 | ≈ 118ms | ≈ 129ms |

**해석**: 현재 부하 수준에서는 풀 30/10으로도 충분하고, 50/20으로 늘려도 처리량·레이턴시 개선폭은 크지 않음. connection 대기 병목이 드러날 만큼의 부하는 아니었음.

---

### 실험 3. 캐시 유무 (목록·상세 Caffeine)

- **목적**: 상품 목록·상세 캐시 적용 시 A·D에서 RPS·p95 변화 확인. B는 목록/상세를 호출하지 않으므로 캐시 영향 없음.
- **바꾼 것**: Caffeine 캐시 적용 여부만 (목록 `itemList`, 상세 `items`, 무효화 정책 동일).
- **나머지**: 1절(캐시만 제외)·2절 동일. 풀 30/10, 비관적 락, 인덱스 O.

| 시나리오 | 지표 | 캐시 없음 | 캐시 있음 |
|----------|------|-----------|-----------|
| A (20 VU 60s) | RPS | ≈ 38.5 | ≈ 39.5 |
| A (20 VU 60s) | p95 | ≈ 38.8ms | **≈ 11.6ms** |
| B (재고 충분) | — | — | 목록/상세 미호출, 비교 생략 |
| D (10 VU 10분) | RPS | ≈ 29.3 | ≈ 29.5 |
| D (10 VU 10분) | p95 | ≈ 118ms | ≈ 119ms |

**해석**: A에서는 목록·상세가 캐시 히트되어 p95가 약 70% 개선. D는 로그인·주문 비중과 `sleep(1)` 때문에 종합 RPS·p95에는 A만큼 개선이 드러나지 않음.

---

### 실험 4. 락 전략 (비관적 vs 낙관적, order-spike만)

- **목적**: 주문 재고 차감 시 비관적 락 vs 낙관적 락(@Version + 재시도)에 따른 처리량·성공률·에러율 비교.
- **바꾼 것**: `order.lock-strategy` 만 `pessimistic` → `optimistic` (프로파일 `perf,perf-optimistic`).
- **나머지**: 1절(락만 제외)·2절 B 동일. 풀 30/10, 캐시 없음, 인덱스 O, 동일 k6·stages·데이터(ITEM_ID=1, 재고 충분).

| 지표 | 비관적 락 | 낙관적 락 |
|------|-----------|------------|
| RPS | ≈ 162 | ≈ 144.7 |
| p95 | ≈ 935ms | ≈ 1170ms |
| http_req_failed | 0% | 23.32% |
| orders_success_201 | ≈ 6594 | 3118 |
| orders_5xx | 0 | 2727 |

**해석**: 동일 아이템에 주문이 몰리는 이 부하에서는 비관적 락이 처리량·성공 건수·에러율 모두 유리. 낙관적 락은 version 충돌·재시도 후 실패가 많아, 스파이크 구간에는 비관적 락이 더 적합.

## 5. 부하 유형 비교 (order-spike vs order-spike-distributed)

여기서는 **동일 조건에서 변수 하나만 바꾼 실험**이 아니라, **부하 유형(스크립트·요청 구성)이 다른 두 시나리오**를 비교합니다.

- **B (order-spike)**: iteration당 로그인 + 주문 1건. 요청 2개/iter. **동일 ITEM_ID=1**에만 주문.
- **C (order-spike-distributed)**: iteration당 로그인 + **목록 조회** + 주문 1건. 요청 3개/iter. **목록에서 랜덤 아이템**으로 주문.

그래서 **RPS(http_reqs)** 는 C가 B보다 큰 것이 자연스럽고(요청 수가 많음), **p95**는 “전체 요청” 기준이라 주문만 따로 보는 것과는 다른 지표입니다.  
같은 stages(0→200 VU 10s, 200 VU 60s)라도 **한 row 락 경합**이 B에서는 크고 C에서는 여러 행에 나뉘어, C에서 p95가 더 낮게 나온 것은 락 분산 효과로 해석할 수 있습니다.

| 지표 | B (동일 아이템) | C (분산) | 비고 |
|------|-----------------|----------|------|
| RPS (http_reqs) | ≈ 161 | ≈ 247 | C는 요청 수가 많아서 RPS가 큼 |
| p95 | ≈ 963ms | ≈ 863ms | 분산으로 락 경합 완화 |
| orders_success_201 | ≈ 6505 | ≈ 6685 | 전체 상품 재고·오픈 충분 시 둘 다 전부 성공 |

- **데이터 조건**: B는 ITEM_ID=1 재고·오픈만 충분. C는 **목록에 나오는 상품 전부** 재고·오픈 충분(예: `UPDATE items SET open_time = ...; UPDATE stocks SET quantity = 10000;`).

## 6. 요약·결론

- **Baseline(3절)**: 공통 조건에서 A≈38 RPS·p95≈39ms, B≈161 RPS·p95≈963ms·주문 성공 ≈6505, C≈247 RPS·p95≈863ms·주문 성공 ≈6685, D≈29 RPS·p95≈118ms. 전 구간 에러율 0%(실험 1 재고 부족 제외).
- **실험 1(재고 수준)**: order-spike에서 재고 부족 시 전부 400 INSUFFICIENT_STOCK, 재고 충분 시 전부 201. 정합성 유지.
- **실험 2(Hikari 풀)**: 30/10 → 50/20 변경 시 현재 부하에서는 개선폭 미미. 풀 30/10으로 충분.
- **실험 3(캐시)**: 목록·상세 캐시로 A의 p95 약 70% 개선. B는 목록 미호출로 영향 없음, D는 혼합 구조 때문에 종합 지표에는 작게만 반영.
- **실험 4(락 전략)**: 동일 아이템 스파이크에서는 비관적 락이 낙관적 락보다 처리량·성공률·에러율 모두 유리.
- **부하 유형(5절)**: order-spike는 동일 아이템 몰림, order-spike-distributed는 분산 주문으로 요청 구성·지표 의미가 다르므로, “동일 조건 실험”이 아닌 “부하 유형별 특성 비교”로 둠.
- **내부 로직 시간**: `OrderService.createOrder()` Micrometer Timer 기준 평균 ≈3~4ms, 최대 ≈112ms. 전체 레이턴시는 DB I/O·네트워크·필터 등 외부 요소 영향이 큼.

#### SLO 대비 (PERF_TEST_PLAN §2 목표 기준)

| 구분 | SLO 목표 | 실측 (Baseline·실험) | 비고 |
|------|----------|----------------------|------|
| **일반 트래픽** | p95 ≤300ms, 5xx <0.5%, 50~100 RPS 안정 | A p95≈39ms ✓, 5xx 0% ✓, RPS≈38.5 | RPS는 50 미만이나 부하 20 VU 기준으로 안정 동작 |
| **일반 트래픽** | — | D p95≈118ms ✓, 5xx 0% ✓, RPS≈29 | soak 10 VU 10분 안정 |
| **타임딜 피크** | p95 ≤500ms, 5xx <1%, 정합성 100% | B p95≈963ms **미달**, 5xx 0% ✓, 정합성 100% ✓ | 피크 구간 p95는 목표 초과. 튜닝·스케일 시 목표 재검토 |
| **타임딜 피크** | — | C p95≈863ms **미달**, 5xx 0% ✓ | 분산 주문도 동일 stages에서 p95 목표 초과 |

- **해석**: 5xx·정합성 목표는 현재 실측에서 충족. 피크 시나리오(B·C)의 p95는 0→200 VU 스파이크·동일 아이템 락 경합 때문에 목표(500ms)를 넘었으며, 목표 조정 또는 스케일/튜닝 후 재측정이 필요하면 PERF_TEST_PLAN §2를 갱신하면 됨.

## 7. 장애/에러 시나리오 (선택)

| 상황 | 사용한 k6 스크립트 | 관찰 항목 | 결과 (측정 시 기입) |
