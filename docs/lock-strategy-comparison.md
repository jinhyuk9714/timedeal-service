# 비관적 vs 낙관적 락 비교

동시에 같은 데이터를 수정할 때 **정합성을 지키는** 두 가지 방식이다.  
**비관적 락**은 “조회 시점에 락을 걸어 한 번에 한 트랜잭션만 갱신”하고, **낙관적 락**은 “락 없이 갱신했다가 충돌하면 version으로 감지·재시도”한다.

---

## 비교표

| 항목 | 비관적 락 (Pessimistic Lock) | 낙관적 락 (Optimistic Lock) |
|------|------------------------------|------------------------------|
| **가정** | 충돌이 자주 발생할 것 | 충돌이 거의 없을 것 |
| **락 거는 시점** | **조회 시점** (`SELECT ... FOR UPDATE`) | **락을 걸지 않음** (갱신 시 version 비교) |
| **방식** | DB 레벨에서 행을 잠가 다른 트랜잭션 차단 | `version`(또는 타임스탬프)으로 “내가 읽은 뒤 누가 먼저 바꿨는지” 감지 |
| **동작** | 먼저 락 잡은 트랜잭션만 갱신, 나머지는 **대기** | 여러 트랜잭션이 동시에 읽고 갱신 시도 → **OptimisticLockException** → **재시도 또는 실패** |
| **적합한 상황** | 동시 수정이 **빈번**한 경우 (예: 같은 상품에 주문 몰림) | 동시 수정이 **드문** 경우 (예: 내 프로필만 수정) |
| **구현** | JPA `@Lock(PESSIMISTIC_WRITE)` → `SELECT ... FOR UPDATE` | 엔티티 `@Version` + `save` 시 version 비교, 예외 시 재시도 |
| **예시** | 재고 차감, 계좌 이체, 티켓팅 | 게시글 수정, 프로필 변경 |

---

## 비관적 락 요약

- **조회할 때** `SELECT ... FOR UPDATE`로 해당 행을 잠근다.
- 락을 잡은 트랜잭션만 그 행을 수정할 수 있고, 나머지는 **락이 풀릴 때까지 대기**한다.
- **장점**: 동시에 한 명만 갱신하므로 정합성 보장이 단순하고, 충돌 시 “대기”만 하면 된다.
- **단점**: 동시 요청이 많으면 대기 시간이 길어져 처리량·레이턴시가 나빠질 수 있다.

---

## 낙관적 락 요약

- **조회 시점에는 락을 걸지 않고**, `version`(또는 타임스탬프)만 읽어 둔다.
- **저장 시점**에 “내가 읽은 version과 DB의 version이 같은가?”를 검사한다.  
  다르면 **OptimisticLockException** → 재시도하거나, 재시도 후에도 실패하면 비즈니스 에러(재고 부족 등)로 처리한다.
- **장점**: 락 대기가 없어서 충돌이 적을 때는 처리량·레이턴시가 좋을 수 있다.
- **단점**: 같은 행을 많이 동시에 고치면 version 충돌·재시도·실패(5xx/4xx)가 늘어난다.

---

## 이 프로젝트에서의 적용

- **재고 차감** 구간에서 두 전략을 **프로퍼티로 전환**할 수 있게 해 두었다.
  - `order.lock-strategy`: `pessimistic`(기본) | `optimistic`
  - **비관적 락**: `StockRepository.findByItemIdWithLock`(SELECT … FOR UPDATE) 후 차감·저장.
  - **낙관적 락**: `Stock`에 `@Version`, `findByItemId`(일반 조회) 후 차감·`saveAndFlush`, `OptimisticLockException` 시 최대 3회 재시도.

- **성능 측정(B-3)**  
  order-spike(동일 상품·재고, 0→200 VU)에서:
  - **비관적 락**: RPS ≈ 162, p95 ≈ 935ms, 에러율 0%, 주문 성공 다수.
  - **낙관적 락**: RPS ≈ 144.7, p95 ≈ 1170ms, http_req_failed 23.32%, 주문 성공·5xx 모두 발생.

  → **동일 상품에 주문이 몰리는 스파이크**에서는, 이 프로젝트 부하 조건에서는 **비관적 락이 처리량·성공률·에러율 모두 유리**했다. 낙관적 락은 version 충돌과 재시도/실패가 많아져 부적합한 편이었다.

  상세 실험 방법·결과표·해석은 [PERF_RESULT 실험 4(락 전략)](perf/PERF_RESULT.md#실험-4-락-전략-비관적-vs-낙관적-order-spike만) 참고.
