# 비관적 vs 낙관적 vs 분산 락 비교

동시에 같은 데이터를 수정할 때 **정합성을 지키는** 방식들이다.  
**비관적 락**은 “조회 시점에 락을 걸어 한 번에 한 트랜잭션만 갱신”하고, **낙관적 락**은 “락 없이 갱신했다가 충돌하면 version으로 감지·재시도”한다.

---

## 비교표

| 항목             | 비관적 락 (Pessimistic Lock)                             | 낙관적 락 (Optimistic Lock)                                                                |
| ---------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **가정**         | 충돌이 자주 발생할 것                                    | 충돌이 거의 없을 것                                                                        |
| **락 거는 시점** | **조회 시점** (`SELECT ... FOR UPDATE`)                  | **락을 걸지 않음** (갱신 시 version 비교)                                                  |
| **방식**         | DB 레벨에서 행을 잠가 다른 트랜잭션 차단                 | `version`(또는 타임스탬프)으로 “내가 읽은 뒤 누가 먼저 바꿨는지” 감지                      |
| **동작**         | 먼저 락 잡은 트랜잭션만 갱신, 나머지는 **대기**          | 여러 트랜잭션이 동시에 읽고 갱신 시도 → **OptimisticLockException** → **재시도 또는 실패** |
| **적합한 상황**  | 동시 수정이 **빈번**한 경우 (예: 같은 상품에 주문 몰림)  | 동시 수정이 **드문** 경우 (예: 내 프로필만 수정)                                           |
| **구현**         | JPA `@Lock(PESSIMISTIC_WRITE)` → `SELECT ... FOR UPDATE` | 엔티티 `@Version` + `save` 시 version 비교, 예외 시 재시도                                 |
| **예시**         | 재고 차감, 계좌 이체, 티켓팅                             | 게시글 수정, 프로필 변경                                                                   |

**분산 락(Redis)**는 위 표에 세 번째 열로 둘 수 있으며, 락 거는 시점=크리티컬 섹션 진입 전 Redis SET NX PX, 방식=상품별 Redis 키·획득 실패 시 재시도/실패, 적합=멀티 인스턴스 재고 차감. 아래 **분산 락(Redis) 요약** 참고.

## 비관적 락 요약

- **조회할 때** `SELECT ... FOR UPDATE`로 해당 행을 잠근다.
- 락을 잡은 트랜잭션만 그 행을 수정할 수 있고, 나머지는 **락이 풀릴 때까지 대기**한다.
- **장점**: 동시에 한 명만 갱신하므로 정합성 보장이 단순하고, 충돌 시 “대기”만 하면 된다.
- **단점**: 동시 요청이 많으면 대기 시간이 길어져 처리량·레이턴시가 나빠질 수 있다.

---

## 낙관적 락 요약

- **조회 시점에는 락을 걸지 않고**, `version`(또는 타임스탬프)만 읽어 둔다.
- **저장 시점**에 “내가 읽은 version과 DB의 version이 같은가?”를 검사한다.  
  다르면 **OptimisticLockException** → 재시도하거나, 재시도 후에도 실패하면 비즈니스 에러(재고 부족 등)로 처리한다.
- **장점**: 락 대기가 없어서 충돌이 적을 때는 처리량·레이턴시가 좋을 수 있다.
- **단점**: 같은 행을 많이 동시에 고치면 version 충돌·재시도·실패(5xx/4xx)가 늘어난다.

---

## 분산 락(Redis) 요약

- **크리티컬 섹션 진입 전** Redis에 `stock:lock:{itemId}` 키를 `SET NX PX`(유효기간 5초)로 잡는다.
- 락을 잡은 경우에만 재고 조회·차감·저장 후, Lua로 “본인 값이면 삭제”하며 해제.  
  락 획득 실패 시 최대 3회 재시도(10ms 대기) 후 실패 시 `INSUFFICIENT_STOCK`(4xx).
- **장점**: 여러 서버/인스턴스가 같은 재고를 다룰 때 DB 행 락만으로는 한계인 경우 대안이 됨.
- **단점**: Redis 의존·네트워크 왕복 추가, 락 경합 시 재시도/실패 증가 가능.

---

## 이 프로젝트에서의 적용

- **재고 차감** 구간에서 **세 전략**을 프로퍼티로 전환할 수 있게 해 두었다.
  - `order.lock-strategy`: `pessimistic`(기본) | `optimistic` | `distributed`
  - **비관적 락**: `StockRepository.findByItemIdWithLock`(SELECT … FOR UPDATE) 후 차감·저장.
  - **낙관적 락**: `Stock`에 `@Version`, `findByItemId`(일반 조회) 후 차감·`saveAndFlush`, `OptimisticLockException` 시 최대 3회 재시도.
  - **분산 락**: `StockLockService.tryLock(itemId)`(Redis SET NX PX) 후 `findByItemId`·차감·저장·해제. 락 실패 시 최대 3회 재시도.

- **성능 측정**  
  order-spike(동일 상품·재고, 0→200 VU)에서:
  - **비관적 락**: RPS ≈ 162, p95 ≈ 935ms, 에러율 0%, 주문 성공 다수.
  - **낙관적 락**: RPS ≈ 144.7, p95 ≈ 1170ms, http_req_failed 23.32%, 주문 성공·5xx 모두 발생.
  - **분산 락**: 프로파일 `perf,perf-distributed`로 동일 k6 실행 후 [PERF_RESULT 실험 4](perf/PERF_RESULT.md#실험-4-락-전략-비관적-vs-낙관적-order-spike만) 표에 열 추가해 비교.

  → **동일 상품에 주문이 몰리는 스파이크**에서는, 이 프로젝트 부하 조건에서는 **비관적 락이 처리량·성공률·에러율 모두 유리**했다. 낙관적 락은 version 충돌과 재시도/실패가 많아져 부적합한 편. 분산 락은 실측 후 위 표와 함께 해석하면 됨.

## 락 타임아웃·재시도 전략

각 전략별로 “얼마나 기다릴지(타임아웃)”와 “실패 시 몇 번·어떤 간격으로 재시도할지”를 정리했다. 운영 시 튜닝·트레이드오프 참고용.

### 요약표

| 전략               | 타임아웃/대기                                    | 재시도                                     | 현재 구현                                                  | 권장·비고                                                               |
| ------------------ | ------------------------------------------------ | ------------------------------------------ | ---------------------------------------------------------- | ----------------------------------------------------------------------- |
| **비관적 락**      | DB 락 대기 시간                                  | 재시도 없음(대기로 처리)                   | JPA 기본, DB `innodb_lock_wait_timeout`(기본 50s)          | 스파이크 시 장시간 대기 방지하려면 **5~10초**로 제한 검토               |
| **낙관적 락**      | —                                                | **최대 3회**, 즉시 재시도                  | 3회 후 `OptimisticLockException` → INSUFFICIENT_STOCK(4xx) | 필요 시 **지수 백오프**(예: 10ms, 20ms, 40ms)로 충돌 완화               |
| **분산 락(Redis)** | 락 TTL **5초**, 획득 실패 시 대기 없이 즉시 실패 | **최대 3회**, **10ms** 고정 대기 후 재시도 | `StockLockService` TTL 5s, 3회×10ms                        | TTL은 “한 번 재고 갱신”에 충분. 재시도 간격·횟수는 설정값으로 분리 가능 |

### 비관적 락: 타임아웃

- **의미**: `SELECT ... FOR UPDATE`로 행을 잡은 뒤, **다른 트랜잭션은 그 락이 풀릴 때까지 대기**한다. 타임아웃이 없으면 대기 시간이 길어질 수 있다.
- **현재**: JPA `@Lock(PESSIMISTIC_WRITE)`만 사용. DB 기본값(`innodb_lock_wait_timeout`, MySQL 보통 50초)에 의존.
- **권장**:
  - **DB 레벨**: `innodb_lock_wait_timeout = 5` 또는 `10`(초)로 줄이면, 락을 오래 못 잡는 요청은 조기 실패하고 클라이언트에 4xx/5xx로 알릴 수 있다.
  - **JPA 레벨**: `LockModeType.PESSIMISTIC_WRITE` + `QueryHints`로 `jakarta.persistence.lock.timeout`(ms) 지정 가능. DB가 지원하면 해당 시간 초과 시 예외 발생.
- **트레이드오프**: 타임아웃을 짧게 주면 “일시적 경합”에서 실패가 늘어날 수 있고, 길게 주면 스파이크 시 대기 큐가 길어져 레이턴시가 나빠진다. 타임딜 피크에서는 **5~10초** 구간부터 실측해 보는 것을 권장.

### 낙관적 락: 재시도

- **의미**: version 충돌 시 `OptimisticLockException` → **재시도**로 성공 가능성을 높인다.
- **현재**: 최대 **3회** 시도, 재시도 간격 없이 **즉시** 재시도. 3회째도 실패하면 `INSUFFICIENT_STOCK`(4xx) 반환.
- **권장**:
  - 재시도 횟수(3)는 유지해도 무방. 동일 부하 실험에서 version 충돌이 많으면 3회로는 부족할 수 있으나, 더 늘리면 레이턴시·DB 부하가 증가.
  - **백오프**: 짧은 대기(예: 10ms, 20ms, 40ms)를 넣으면 순간적인 동시 갱신 폭주를 조금 분산시킬 수 있다. 구현 시 `Thread.sleep` 또는 스케줄러/Reactor `delay` 등으로 적용 가능.
- **트레이드오프**: 백오프를 넣으면 평균 레이턴시는 소폭 늘어나고, 재시도로 인한 성공은 늘어날 수 있다. “동일 상품 몰림”이 심한 스파이크에서는 이 프로젝트 실측처럼 **비관적 락**이 더 유리한 경우가 많다.

### 분산 락(Redis): TTL·재시도

- **의미**: Redis `SET key value NX PX ttl`로 락을 잡고, **TTL**이 지나면 자동 해제되어 데드락을 방지한다. 획득 실패 시 **재시도**로 기회를 준다.
- **현재** (설정으로 조정 가능):
  - **TTL**: `order.distributed-lock.ttl-seconds` (기본 5). 재고 조회·차감·저장이 이 시간 안에 끝나도록.
  - **재시도**: `order.distributed-lock.max-retries`(기본 3), `order.distributed-lock.retry-sleep-ms`(기본 10). 3회 모두 실패 시 `INSUFFICIENT_STOCK`(4xx).
  - 설정 파일: `application-perf-distributed.yml` (프로파일 `perf-distributed` 사용 시).
- **권장**:
  - TTL은 **5초** 유지. 비즈니스 로직이 늘어나면 5초를 넘지 않도록 로직을 나누는 것이 안전.
  - 재시도 간격·횟수는 yml에서 부하 실험으로 조정. 10ms보다 길게 주면 성공률이 조금 올라갈 수 있으나 레이턴시가 증가.
- **트레이드오프**: 분산 락은 Redis 왕복·경합 때문에 “동일 상품 몰림”에서 실패율이 높게 나온 실측이 있다. 재시도·TTL만으로 한계가 있으면, **비관적 락** 또는 상품별 샤딩 등 구조적 완화를 검토하는 것이 좋다.
